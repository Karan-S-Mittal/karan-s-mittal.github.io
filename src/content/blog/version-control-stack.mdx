“Version control” often names several systems at once: Git’s local data model, the server boundary that accepts or rejects ref updates, a review database, and an execution plane for CI jobs. Treating those systems as one product hides the boundaries that matter during migration, incident response, and security review.

This essay builds a narrower model. It separates four responsibilities and ties each factual claim to Git documentation, a review protocol’s own documentation, an official project guide, or a published specification.

## 1. Git stores objects; refs make history reachable

Git’s current data-model documentation names four object types: **commits, trees, blobs, and tag objects**. Each object has an identifier derived from its type and contents, and an object does not change after creation. A branch is not a mutable line of commits; it is a reference whose value identifies a commit. The repository layout also distinguishes the object store under `objects` from references under `refs`. See the official [Git data model](https://git-scm.com/docs/gitdatamodel) and [repository layout](https://git-scm.com/docs/gitrepository-layout).

Loose objects are not the only physical representation. Git consolidates repository data into packfiles, and its pack format supports both whole objects and deltified representations. That storage optimization does not change the logical identity of an object. The exact format is specified in [gitformat-pack](https://git-scm.com/docs/gitformat-pack).

This gives us the first boundary:

```text
immutable objects  +  movable refs  =  reachable project history
```

Review comments, approval policy, organization membership, and CI status are not part of that core model. A hosting platform can associate those records with object IDs and refs, but it maintains them in additional systems.

## 2. A push crosses a policy boundary

On the receiving side, `git-receive-pack` accepts objects and proposed ref updates. Incoming objects are placed in a quarantine directory before the `pre-receive` hook completes. A non-zero `pre-receive` result prevents the ref updates; accepted objects move into the main object store only after that gate. These are specified behaviors, not a hosting-vendor convention. See [git-receive-pack](https://git-scm.com/docs/git-receive-pack) and [githooks](https://git-scm.com/docs/githooks).

That mechanism is enough to explain where a forge can enforce a subset of repository policy. The forge may add identity, authorization, protected-branch rules, merge queues, and review state around the Git transaction. The implementation varies, but the architectural question stays stable:

> Which system is authoritative for permission, review state, ref mutation, job execution, and produced artifacts?

The boundaries are useful even when one vendor operates every layer. They tell you what must be exported during a migration and which subsystem can fail without corrupting the others.

## 3. Review systems choose different identities

Code review is not one protocol. The most important distinction is the identity a system uses to carry a review across revisions.

### Branch and pull-request review

GitHub defines a pull request as a proposal to merge changes from one branch into another. The hosting service maintains the conversation, checks, and review state around those branches; that state is not encoded in Git’s object database. See GitHub’s official [pull-request overview](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/proposing-changes-to-your-work-with-pull-requests/about-pull-requests).

### Gerrit Change-Id review

Gerrit associates successive commits with one review by using a `Change-Id` footer in the commit message. Amending or rebasing changes the commit ID, while preserving the `Change-Id` lets Gerrit attach the new patch set to the existing review. Gerrit documents the creation and matching rules in [Change-Ids](https://gerrit-review.googlesource.com/Documentation/user-changeid.html).

### Patch-series review

The Linux kernel process distributes patches and patch series by email, expects revisions to be labelled, and asks contributors to preserve patches as plain text. Its guide is explicit about versioned series, recipients, and follow-up. See [Submitting patches](https://docs.kernel.org/process/submitting-patches.html) and the companion [email-client guidance](https://docs.kernel.org/process/email-clients.html).

None of these topologies makes a commit correct by itself. The topology determines how authors, reviewers, revisions, and integration are connected. Test quality, change size, reviewer attention, and integration discipline remain separate variables.

## 4. CI introduces a second execution trust boundary

A repository host can schedule work, but a runner executes it. That distinction matters because workflow code can read checked-out source, invoke tools, use credentials, access networks, and produce artifacts.

GitHub’s self-hosted-runner documentation makes the ownership boundary explicit: the user deploys and manages the machine, while the runner application connects it to GitHub Actions. GitHub also warns that self-hosted runners do not need to start from a clean instance for every job. See [About self-hosted runners](https://docs.github.com/en/actions/concepts/runners/self-hosted-runners) and [Secure use reference](https://docs.github.com/en/actions/reference/security/secure-use).

Container images can improve consistency, but an image is not a proof of a hermetic build. The OCI Image Specification defines a manifest, configuration, and ordered filesystem layers. It does not, by itself, fix network responses, injected secrets, mutable external services, clock state, runner kernel behavior, or unpinned inputs. This is an inference from the scope of the [OCI Image Specification](https://github.com/opencontainers/image-spec/blob/v1.1.1/spec.md) and its [image configuration](https://github.com/opencontainers/image-spec/blob/v1.1.1/config.md).

A useful review therefore separates three questions:

- Is the **image** content-addressed and pinned?
- Is the **job environment** isolated and cleared between trust domains?
- Are the **inputs and outputs** identified, retained, and verifiable?

## 5. Design the boundaries before choosing the platform

The model leads to a practical architecture checklist:

| Responsibility | Authoritative record | Failure question |
|---|---|---|
| Source history | Git objects and refs | Can history be fetched and refs be reconstructed? |
| Review state | Forge or review database | Can comments, approvals, and revision identity be exported? |
| Policy | Rules plus receive/integration gates | Which actor can mutate a protected ref? |
| Execution | Runner control plane and worker | What code shares a machine, credential, cache, or network? |
| Artifacts | Registry or artifact store | Can an output be traced to source, workflow, and inputs? |

This is the decision point: do not ask only whether a product “supports Git” or “has CI.” Ask which records live outside Git, which boundaries execute untrusted code, and which identifiers survive a migration.
