When discussing Large Language Models, conversations frequently focus on compute: FLOPS, parameter counts, and matrix multiplication throughput.

Yet in autoregressive production serving, memory capacity and movement can become the limiting resources: a request's KV cache grows with context, while the decoder must read that cache at every step.

To understand how a high-throughput engine such as **vLLM** addresses this problem, let us build the mental model slowly from first principles:
1. How text is generated token-by-token.
2. Why the naive approach incurs quadratic redundant computation.
3. How caching intermediate representations created the **KV-Cache**.
4. How model architectures evolved (MHA &rarr; MQA &rarr; GQA) to shrink this cache.
5. The hidden crisis: why pre-reserving contiguous KV memory wastes capacity under variable-length workloads.
6. How borrowing a virtual-memory idea lets **PagedAttention** manage that memory in fixed-size blocks.

## 1. The Naive Decoding Loop: The Quadratic Trap

Autoregressive language models generate text **one token at a time**. Each new token depends on all the tokens that came before it.

Imagine a generation prefix beginning with `"The"`. The next tokens might be `"quick brown fox"`.

### What Happens Inside Self-Attention?
In standard multi-head self-attention, every token in the sequence is projected into three vectors via learned weight matrices:
* **Query (`Q`):** What this token is looking for.
* **Key (`K`):** What this token contains (its indexable identity).
* **Value (`V`):** The actual contextual information to extract.

The attention calculation scores the current query against every key, normalizes those scores, and uses them to mix the values:

$$
\operatorname{Attention}(Q, K, V) = \operatorname{softmax}\!\left(\frac{QK^{\mathsf T}}{\sqrt{d_k}}\right)V
$$

<p class="formula-note"><strong>How to read it.</strong> <code>QKᵀ</code> compares a query with each key. Dividing by <code>√dₖ</code> keeps those scores numerically well-scaled; <code>softmax</code> turns them into weights; multiplying by <code>V</code> forms the weighted context vector.</p>

### The Naive Flaw
If we implement this naively, look at what happens at each decoding step:

* **Step 1:** Pass `["The"]` through the entire Transformer &rarr; compute `Q₀`, `K₀`, `V₀` &rarr; generate `"quick"`.
* **Step 2:** Pass `["The", "quick"]` through the entire Transformer &rarr; recompute `Q₀`, `K₀`, `V₀` *and* compute `Q₁`, `K₁`, `V₁` &rarr; generate `"brown"`.
* **Step 3:** Pass `["The", "quick", "brown"]` through the entire Transformer &rarr; recompute `Q₀`, `K₀`, `V₀`, recompute `Q₁`, `K₁`, `V₁`, *and* compute `Q₂`, `K₂`, `V₂` &rarr; generate `"fox"`.

```
Step 1: [T]                 --> 1 token projected
Step 2: [T, q]              --> 2 tokens projected (1 redundant!)
Step 3: [T, q, b]           --> 3 tokens projected (2 redundant!)
Step N: [T, q, b, ..., N]   --> N tokens projected (N-1 redundant!)
```

To generate a sequence of `N` tokens this way, the model repeatedly re-projects past tokens: $1 + 2 + \dots + N = O(N^2)$ token projections. KV caching removes that repeated projection work. It does **not** make ordinary dense attention free: at step `t`, the current query still attends over `t` cached keys and values, so the attention read grows with context length. [1]

## 2. The Breakthrough: The KV-Cache

Notice a crucial mathematical property of autoregressive decoding:

> **The keys (`K`) and values (`V`) of past tokens depend only on their past context. Because past tokens never change, their cached vectors remain static across future decoding steps.**

Only the **query (`Q`)** needs to come from the *current newly generated token*, because only the current token is asking: *"Which past tokens should I attend to?"*

### The KV-Cache Solution
Instead of recomputing past keys and values on every forward pass, we calculate them **once** when each token is first seen, and save them in GPU device memory.

<NaiveVsKVCacheArchitecture
  exhibit="01"
  title="Naive recomputation vs. KV caching"
  caption="At decoding step 3, naive decoding recomputes all past token projections; KV caching reuses stored tensors in GPU VRAM and projects only the single active token."
/>

During **prefill**, the model processes the prompt and materializes the prompt's keys and values. During **decode**, each new token supplies a fresh `Q`, `K`, and `V`; the new `K` and `V` are appended while the query reads the accumulated cache. The exact kernel organization varies by model and implementation, but this prefill/decode distinction is the basis of KV caching. [1]

With the KV-cache in place:
1. When generating step `t`, we project **only the single new token** to get `Qₜ`, `Kₜ`, and `Vₜ`.
2. We append `Kₜ` and `Vₜ` to the stored KV cache in memory.
3. `Qₜ` attends over all stored keys `[K₀, K₁, …, Kₜ]` and retrieves from `[V₀, V₁, …, Vₜ]`.
4. The projection work for the new token is constant with respect to the already-generated sequence. The attention operation still reads the growing cache; KV caching removes recomputation, rather than changing dense attention's quadratic-in-sequence-length total attention work. [1]

We traded redundant compute for memory storage. But how much memory does this cache actually consume?

## 3. The Anatomy & Evolution of KV Cache Heads

Let us calculate the memory footprint of storing Key and Value states for a single token.

For a model with:
* `L` layers
* $H_{\mathrm{kv}}$ key-value attention heads
* $d_{\mathrm{head}}$ dimension per head
* 16-bit precision (`FP16` or `BF16` = 2 bytes per element)

Every token reserves two tensors—one key and one value—at every layer:

$$
M_{\text{KV/token}} = 2 \cdot L \cdot H_{\mathrm{kv}} \cdot d_{\mathrm{head}} \cdot b
$$

<p class="formula-note"><strong>How to read it.</strong> <code>L</code> is the layer count, <code>Hₖᵥ</code> the number of KV heads, <code>d<sub>head</sub></code> the width of each head, and <code>b</code> the bytes per element. For FP16 or BF16, <code>b = 2</code>, so the expression becomes <code>4 × L × Hₖᵥ × d<sub>head</sub></code> bytes per token.</p>

### The Architectural Evolution: MHA &rarr; MQA &rarr; GQA

Because the KV cache grows linearly with sequence length and batch size, AI researchers developed architectural variants to shrink $H_{\mathrm{kv}}$:

<KVEvolutionArchitecture
  exhibit="02"
  title="What changes from MHA to GQA to MQA"
  caption="With eight query heads held constant, MHA stores eight K/V head sets, the illustrated GQA configuration stores two, and MQA stores one. The relative K/V cache footprint falls in the same ratio."
/>

#### 1. Multi-Head Attention (MHA — 2017)
* **$H_{\mathrm{kv}} = H_q$**: Every query head has its own dedicated key and value head (1:1).
* **Footprint:** For an illustrative 80-layer model with 64 KV heads, 128 dimensions per head, and BF16 cache entries, an 8,192-token sequence occupies about 20 GiB of KV cache. The point is the linear scaling: double the sequence count or batch occupancy and the cache requirement doubles.

#### 2. Multi-Query Attention (MQA — Shazeer, 2019)
* **$H_{\mathrm{kv}} = 1$**: All query heads share a single key head and a single value head (`N:1`).
* **Footprint:** Relative to MHA, KV-cache storage shrinks by exactly $H_q$ for the same layer count, head dimension, precision, and sequence length. Shazeer introduced the design to reduce the memory-bandwidth cost of incremental decoding, reporting a modest quality trade-off in the evaluated models. [2]

#### 3. Grouped-Query Attention (GQA — Ainslie et al., 2023)
* **$1 < H_{\mathrm{kv}} < H_q$**: Several query heads share each KV head. The diagram uses four query heads per KV head; the exact ratio is a model decision.
* **Footprint:** Relative to MHA, storage shrinks by $H_q / H_{\mathrm{kv}}$. GQA was proposed as the intermediate point between MHA and MQA, with an uptraining recipe for converting existing multi-head checkpoints. [3]

## 4. The Hidden Crisis: Contiguous Memory Allocation

Even when GQA reduces tensor dimensions, a serving system must still manage a KV cache that grows and shrinks independently for every active request.

Why? The culprit was not the math—it was **memory allocation strategy**.

### Why Serving Engines Often Start With Contiguous Buffers
The usual tensor abstraction presents a contiguous logical region. If a server reserves one large contiguous region per request, it has to choose a capacity before it knows the request's final output length.

To avoid continuous dynamic reallocations, serving engines adopted a conservative approach: [4]
> **When a new request arrives, allocate a contiguous memory buffer sized for the maximum possible sequence length (e.g., 4,096 or 8,192 tokens) upfront.**

<MemoryFragmentationArchitecture
  exhibit="03"
  title="Why maximum-length reservation wastes capacity"
  caption="The example request has produced five tokens. Contiguous allocation holds twelve slots for it; fixed-size allocation requests frames as the sequence grows and leaves unused space only in the active final block."

### The Three Sins of Contiguous Allocation

1. **Over-allocation:** The server reserves slots for tokens that may never be generated. A short completion leaves a tail that no other request can use while the reservation lives.
2. **Internal Fragmentation:** Because the engine cannot predict when the model will output the `<eos>` (end-of-sequence) token, if generation terminates at token 400 of an 8,192 buffer, the remaining 7,792 allocated slots are permanently wasted for that request's lifetime.
3. **External Fragmentation:** Over time, requests of varying lengths start and terminate at different moments. The GPU device-memory pool can become a "swiss cheese" of non-contiguous free chunks.

In the conventional systems evaluated by the PagedAttention paper, only 20.4–38.2% of allocated KV-cache capacity held actual token states; the corresponding 61.8–79.6% waste is a result for those baselines and workloads, not a universal constant. [4]

## 5. The Operating System Epiphany

In computer systems engineering, this problem is not new. Operating systems solve an analogous allocation problem with virtual memory.

The OS solution was **Virtual Memory Paging**:
1. Break user process memory into fixed-size **Virtual Pages**.
2. Break physical RAM into matching fixed-size **Physical Frames**.
3. Use a **Page Table** to map any virtual page to any physical frame anywhere in RAM.
4. Physical memory no longer needs to be contiguous.

In 2023, Woosuk Kwon and researchers at UC Berkeley asked a breakthrough question:

> *Why can't an LLM KV-cache work exactly like an operating system page table?*

This insight became **PagedAttention**, the memory-management technique introduced with **vLLM**. [4]

## 6. PagedAttention Built Step-by-Step

PagedAttention decouples the **logical token stream** from **physical GPU device-memory allocation** through a per-sequence block table. [4]

Let us walk through how a sequence transforms through four progressive stages:

<PagedAttentionStepsArchitecture exhibit="04" title="Logical blocks → block table → physical frames" caption="Logical token blocks remain ordered in the request while a block table maps them to any available physical GPU frames. The attention kernel follows that table directly when reading K/V data." />

### Step 1: Virtual Blocks (Logical Slicing)
When a request enters the engine, its logical token stream is partitioned into small, fixed-size **logical blocks** (typically 16 tokens; shown with block size $B = 4$ in the diagram for clarity):
* **Logical Block #0:** Contains tokens `t₀` to `t₃` (`"The", "quick", "brown", "fox"`).
* **Logical Block #1:** Contains tokens `t₄` to `t₆` (`"jumps", "over", "lazy"`), with slot `t₇` open for the next token.
* No memory is reserved for distant future tokens upfront.

### Step 2: The Block Table (Virtual-to-Physical Translation)
Like an OS page table, the engine maintains a lightweight **Block Table** for each request:
* **Logical Block #0** &rarr; **Physical Frame #12**
* **Logical Block #1** &rarr; **Physical Frame #04**
* Translation is a constant-time $O(1)$ index lookup.

### Step 3: Scattered Physical Allocation in GPU Device Memory
The engine allocates physical frames from a pre-allocated global pool wherever space exists:
* Frame `#12` and Frame `#04` are placed in non-contiguous locations in GPU device memory.
* Remaining frames can be assigned to other requests without finding a large contiguous span.
* The allocator's unit is a fixed-size block, so each sequence need leave at most its final partially filled block unused. The exact overhead depends on block size and the active sequence mix. [4]

### Step 4: In-Kernel Block Gather
If physical memory is scattered, how does the GPU consume the sequence without first assembling a contiguous tensor?

The attention kernel receives the block table and uses it to address the KV blocks directly. This indirection lets it consume a logical sequence whose physical blocks are scattered, without first materializing one contiguous KV tensor. The important claim is not that every implementation has identical register or shared-memory traffic; it is that PagedAttention removes a separate *materialization copy* before attention. [4]

## 7. The Superpower: Zero-Copy Sharing & Copy-on-Write

Decoupling logical sequences from physical memory makes **zero-copy memory sharing** practical for a serving system. [4]

<CopyOnWriteArchitecture
  exhibit="05"
  title="Zero-copy sharing and copy-on-write"
  caption="Shared prompt blocks live once in physical device memory with ref_count=2; private physical frames are allocated only after generation branches diverge."
/>

### 1. Parallel Sampling and Beam Search
When several candidate continuations begin from one prompt:
* The prompt tokens are stored **once** in physical memory (`Frame #12`, `Frame #04`) with a reference counter (`ref_count = 2`).
* Both parallel output streams point their block tables to the identical physical frames.
* When a branch must write to a shared block, the engine allocates a private physical frame and copies that block before the write: **Copy-on-Write (CoW)**. If divergence starts at a new block, no copy of the already-complete prompt block is needed.
* The saving is proportional to the shared prefix: one physical copy of the prompt is retained until a branch needs to write a shared block. [4]

### 2. Prefix Caching Is a Separate Scheduling Policy
Paged blocks make shared prefixes possible; they do not decide which prefixes to retain. The PagedAttention paper describes sharing predefined common prefixes; choosing what to retain, match, and evict is a separate implementation policy. Such a prefix cache can avoid repeated prefill work for repeated prompts, but its time-to-first-token effect depends on hit rate, model, and scheduler. Treat it as an implementation-level optimization, not an automatic consequence of PagedAttention. [4]

## 9. Summary & Systems Takeaways

Transforming KV-cache management from rigid static buffers to dynamic virtual paging fundamentally transformed LLM serving economics:

| Dimension | Contiguous Allocation | PagedAttention |
|---|---|---|
| **Memory Waste** | Can be high under pre-reservation and duplication | Near-zero tail waste within the block pool, plus implementation overhead |
| **External Fragmentation** | Large contiguous reservations can fail despite aggregate free memory | Block-level admission avoids request-sized contiguous extents |
| **Batch Size Capacity** | Constrained by worst-case max length | More flexible block-level admission |
| **Serving Throughput** | Baseline depends on workload and scheduler | vLLM reported 2–4× versus FasterTransformer and Orca at comparable latency in its evaluation; this is not a universal constant [4] |
| **Prefix & Prompt Sharing** | Duplicate full tensors | **Shared block aliases; CoW on write** |

### The Core Architectural Lesson

The story of PagedAttention illustrates a fundamental principle in modern AI infrastructure:

> **The most critical breakthroughs in modern machine learning systems often come from applying classical computer systems engineering principles to AI memory access patterns.**

When serving throughput is constrained, inspect the memory layout before changing the model: fixed-size blocks, explicit translation, and sharing policies can remove request-sized allocation constraints while keeping the trade-offs visible.
